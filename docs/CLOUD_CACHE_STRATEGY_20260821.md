# switch 网关理解 + 云厂商上下文缓存策略设计

> 2026-08-21 · 讨论稿（非实现承诺）。目标: ① 完整理解 switch 现状;
> ② 把「心跳预热 / 固化前缀 / 滚雪球」与「负载均衡 × 高缓存命中」的
> 矛盾讲清楚; ③ 给出可落地的设计, 供讨论后进入实现。

---

## 〇、TL;DR

云厂商上下文缓存是**前缀精确匹配**（token 0 起完全一致才命中），这决定了
网关层的两个设计铁律：

1. **前缀必须稳定** —— 同一逻辑上下文（系统提示 + 知识块 + 会话历史）在
   所有请求里必须以完全相同、相同顺序的 token 出现（固化前缀）。
2. **同前缀必须同节点** —— 同一前缀的请求尽量固定到同一 provider/实例，
   否则缓存被路由打散（负载均衡与缓存局部性的矛盾）。

在此基础上，三个机制放大命中：

- **心跳预热**：在云厂商缓存 TTL 内周期性发最小请求，让高价值长前缀
  不因空闲而过期（DeepSeek ~5min / OpenAI 5–10min / Anthropic 5min|1h）。
- **固化前缀**：把「稳定块」前置并规范化（去时间戳/随机噪声/顺序漂移），
  让命中前缀尽可能长——这是成本的核心杠杆。
- **滚雪球**：共享前缀随请求累积变长、变值钱；网关按 租户→项目→会话 聚合
  前缀，让多轮对话/多用户共享同一前缀，命中块越滚越大。

路由分发则用**两级结构**解决矛盾：前缀级「一致哈希亲和」保缓存局部性，
provider 内部「加权随机/容量感知」保负载均衡。

## 一、switch 现状盘点（2026-08-21）

### 1.1 两层缓存已存在

**① 网关响应缓存（内存 LRU + TTL）** —— `cache/cache.go`

- 键 = `hash(requestCacheKey, provider|model|api_key|X-Context-Hash)`，
  跨租户/跨模型/跨 provider 隔离（2026-08-19 修复）。
- `X-Context-Hash`：DialogMesh 编译上下文稳定哈希（sha256[:32]），
  相同编译上下文即使消息格式有差异也能命中网关响应缓存。
- 命中 → 直接返回，0 上游调用；当前 `1000 条 / 5min TTL`。

**② 上游上下文缓存命中透传（观测层）** —— `provider/interface.go`

- `TokenUsage` 归一三维度：OpenAI `cached_tokens` / DeepSeek
  `prompt_cache_hit_tokens` / Anthropic `cache_read_input_tokens`
  → `Cached() / CachedMiss()`。
- metrics 有 `prompt_cache_hit_rate`，计费按命中价折算。

### 1.2 现状缺口（正是本设计要补的）

| 能力 | 现状 | 缺口 |
|------|------|------|
| 响应缓存 | ✅ 有（全量请求级） | 无前缀级缓存；TTL 固定 5min 无分层 |
| 前缀缓存观测 | ✅ 透传命中 token | 无「哪段前缀命中/多大块」粒度 |
| 前缀固化 | ❌ 无 | 消息顺序/噪声由调用方随意决定 |
| 心跳预热 | ❌ 无 | 高价值前缀空闲即过期 |
| 路由亲和 | ❌ 无 | 同前缀请求可能被加权随机打散到不同 provider |
| 滚雪球 | ❌ 无 | 无前缀聚合/统计/复用机制 |

## 二、云厂商上下文缓存机制（2026-08 实测口径）

> 统一规律：**自动 / 前缀精确匹配 / 命中打折计费**。命中与否 = 前缀
> 是否完全一致，与「网关响应缓存」是两回事（一个省上游算力+钱，
> 一个省网关→上游的整个往返）。

| 厂商 | 启用方式 | 最小可缓存前缀 | 命中折扣 | 写入成本 | TTL（空闲过期） |
|------|----------|----------------|----------|----------|------------------|
| DeepSeek V4 | 自动，零配置 | ~1,024 tokens（64-token 单元） | 输入大折扣（面板口径，历史 50×） | 无 | ~5 min |
| OpenAI | 自动 + 显式 breakpoint（`prompt_cache_options`） | 1,024–2,048 tokens（模型相关），按 128-token 递增 | 命中输入约 -50%~-90% | 有写开销（部分模型） | 5–10 min 无活动；显式 ttl 默认 30m |
| Anthropic | 手动 `cache_control` breakpoint（最多 4 个） | ≥1,024 tokens | 命中输入 -90%（5m）/ -75%（1h） | 写有 25% 附加 | 5m 默认 / 1h 可选 |
| Gemini | 隐式自动（≥32k）+ 显式 cached content | ~32k tokens（隐式）；显式无下限 | 隐式命中 -75%（1h TTL） | 显式有存储费 | 1h（隐式）；显式可配 |

### 2.1 关键机制细节

**OpenAI 的引擎路由与节流（对本设计最重要）**

- 官方按「prompt 前 ~256 tokens 的哈希」把请求路由到推理引擎 —— 也就是
  **云侧自己就在做前缀亲和**；我们侧打散前缀 = 和云侧对着干。
- 每个前缀/每个 key 流量建议 ≈ **15 req/min**，超了部分会 miss。
  → 预热频率、并发必须受控，且同前缀流量要收敛（亲和）。
- 显式 breakpoint（`prompt_cache_options.ttl`）可把前缀固定成多个缓存块。

**DeepSeek 的 64-token 单元**

- 前缀按 64-token 单元对齐，命中块 = 从 token 0 起的最大一致段。
- 命中输入价历史折扣大（面板口径 96% 命中率的案例是真实可达到的）。

**Anthropic 的 4 breakpoint**

- 最多 4 个 `cache_control`：常见策略 = 系统提示 + 最后 3 条非系统消息。
- 网关需在 Anthropic 请求体里按结构化位置注入 breakpoint（现网关是
  OpenAI 兼容转发，Anthropic 直连需独立协议处理）。

## 三、三大机制设计

### 3.1 固化前缀（Prefix Stabilization）—— 一切的前提

目标：同一逻辑上下文的 token 前缀**逐字节一致**。

**请求侧（DialogMesh 编译器）**

1. **稳定块前置**：`[系统提示][稳定知识/工具定义][会话历史][本轮输入]`
   —— 长稳定块放最前，命中长度才大。
2. **禁止时间戳/随机噪声进前缀**：当前时间、request_id、随机 id 放
   消息尾部或 header，不参与前缀。
3. **顺序规范化**：工具列表按名称排序；知识块按稳定 id 排序。

**网关侧（switch）**

4. **前缀规范化管线**（可选，防调用方不规范）：对进入的消息流做
   `normalize_prefix` —— 剥离尾部噪声、对 system 块做 whitespace 归一、
   检测顺序漂移并提示（不做强改，改动会破坏字节一致性）。
5. **前缀指纹**：`PrefixFingerprint(messages) = sha256(stable_blocks)`，
   与响应缓存键解耦 —— 用于统计「同一指纹的命中率/频次」，识别高价值前缀。

### 3.2 心跳预热（Heartbeat Prewarm）

目标：高价值长前缀在 TTL 内不被清出，维持「热」。

**触发条件**

- 前缀指纹满足：`近 N 分钟请求 ≥ 阈值` 或 `命中 token 总量 ≥ 阈值`
  （高价值），且当前距上次请求已接近 TTL 的 50%（DeepSeek ~2.5min）。

**执行方式**

- `WarmScheduler` 后台协程：对热前缀周期发**最小成本请求**
  （`max_tokens=1`，复用同一前缀 + 1 token 尾），标记 `X-DM-Warmup: 1`
  header，避免污染业务计费/指标（预热请求单独记 `warmup_requests`）。
- 频率按厂商节流：OpenAI 每前缀 ~15 req/min 上限 → 预热 ≈ 每 2–4min
  一次；DeepSeek TTL 5min → 每 3min 一次。
- **只预热当前路由会选中的 provider**（亲和决定），不跨 provider 重复
  预热（省写成本 + 省厂商配额）。

**验收**：连续空闲 15min 后，`prompt_cache_hit_rate` 不回落到 0。

### 3.3 滚雪球（Snowball Accumulation）

目标：让可共享前缀越滚越大、越滚越值钱。

**前缀聚合层次**

```
全局稳定块（系统提示 + 平台知识）      ← 所有租户共享, 最大滚雪球
  └ 租户块（租户级知识/人格/风格）     ← 同租户共享
     └ 项目块（项目语料/约束）         ← 同项目共享
        └ 会话块（对话历史折叠）       ← 同会话共享
           └ 本轮输入（不可缓存部分）
```

- 每层独立成块，层间顺序固定；上层块被更多人共享 → 命中面大。
- 会话块用「历史折叠」：多轮对话把早期历史凝练成摘要占位，保持前缀
  长度稳定而非无限增长（过长前缀有边际收益递减 + 计费基数增大）。

**网关统计与反馈**

- `PrefixProfiler`：按指纹记录 `hit_tokens / total_tokens / req_count /
  last_access`，定期输出「命中块分布」——看到底哪段在滚雪球。
- 反馈给请求侧：命中率低的层（如项目块太杂）→ 提示拆块/固化。

## 四、负载均衡 × 高缓存命中（路由分发设计）

### 4.1 矛盾的本质

- 缓存局部性要求：**同前缀 → 同 provider/实例**（前缀越集中越热）。
- 负载均衡要求：流量**均匀分散**到多 provider，避免单点/单商故障与限流。

两者直接冲突。业界解法 = **两级路由**（OpenAI 云侧自己就是按前缀哈希
路由到引擎的，我们网关层做同样的事）。

### 4.2 两级路由

```
请求
 ├─ 规则层（意图/复杂度 → provider 组/模型档位）      ← 已实现 2026-08-21
 │
 ├─ 亲和层（新）: hash(前缀指纹 + 租户) → 组内稳定 provider
 │    —— 同一前缀固定同一 provider, 保缓存局部性
 │    —— 用一致哈希环（chash）: provider 增减只影响环段,
 │       同前缀仍尽量落在同节点
 │
 └─ 节点层: provider 内部加权随机（weight/health/latency/cost）
       —— 已实现, 用于无亲和要求的新前缀/冷前缀
```

**关键规则**

1. **冷启动**：新前缀第一次出现 → 节点层加权随机选最优 provider；
   选中后**绑定**（`prefix → provider` 亲和表），后续同前缀走亲和。
2. **容量/故障溢出**：亲和 provider 熔断/超载 → 溢出到次优 provider
   并标记；恢复后流量**逐渐迁回**（避免来回抖动把缓存打碎）。
3. **多前缀并行**：一个请求可拆多个前缀块（系统块/租户块/项目块），
   各块独立亲和 —— 上层块（系统/租户）可跨 provider 共享统计，但
   实际预热只跟「主前缀」的亲和 provider。
4. **与智能路由规则的关系**：规则层决定 provider 组（如 casual→本地组、
   complex→云端强模型组）；亲和层在组内选稳定节点 —— 不冲突。

### 4.3 一致性哈希实现要点

- 哈希键：`hash(prefix_fingerprint + tenant_id)`，环上分布 256 虚拟节点。
- provider 权重映射到环段宽度（weight 大 → 段宽大 → 承担更多前缀）。
- 查询：顺时针找第一个可用 provider；不可用 → 跳过（溢出链）。
- 亲和表 TTL：随前缀热度续期，冷前缀自然回收。

## 五、与现有智能路由的融合（落地路线）

### 阶段 A（已就绪）

- 规则层（意图/复杂度）+ 池内加权随机 —— 已实现、已推送。
- 前缀缓存透传指标（`prompt_cache_hit_rate`）—— 已实现。

### 阶段 B（本设计的核心实现）

1. **前缀指纹 + PrefixProfiler**：统计命中分布，识别高价值前缀。
2. **亲和路由（一致哈希）**：`prefix → provider` 绑定 + 溢出 + 迁回。
3. **固化前缀规范**：DialogMesh 编译器固定块顺序；网关 normalize 提示。
4. **WarmScheduler 心跳预热**：按厂商 TTL/节流参数调度，`X-DM-Warmup`
   标记隔离。
5. **响应缓存分层 TTL**：高价值前缀的响应缓存 TTL 拉长（5min → 30min+），
   低价值保持短。

### 阶段 C（进阶）

- Anthropic 直连 breakpoint 注入（4 缓存块）；OpenAI `prompt_cache_options`。
- 多级前缀块（系统/租户/项目/会话）独立亲和与统计。
- 成本报表：按「命中/未命中 token 金额」对比，验证滚雪球收益。

## 六、指标与验收

| 指标 | 目标 |
|------|------|
| `prompt_cache_hit_rate` | 稳定 ≥ 80%（DeepSeek 口径，参照面板案例 96%） |
| 同前缀请求 miss 率 | 亲和层生效后，同前缀 miss 不因路由打散而上升 |
| 预热成本 | 占输入 token 总量 < 2% |
| 负载均衡 | 各 provider 吞吐偏离 ≤ 20%（故障/冷启动除外） |
| 响应缓存命中 | 维持现有 ~99%（网关层） |

## 七、待讨论问题

1. **前缀块由谁固化**：网关强规范（风险：改字节破坏一致性）vs 请求侧
   负责（DialogMesh 编译器）+ 网关只统计/提示？倾向后者。
2. **预热成本归属**：按租户计费还是网关平台成本？
3. **一致哈希 vs 简单 LRU 绑定**：前缀数量大时，哈希环更稳；前缀少时
   直接 `map[prefix]provider` 更简单 —— 起点用哪个？
4. **OpenAI 15 req/min 节流**：预热与真实请求共享配额，需要协调器
   统一调度（真实请求优先）。
5. **Anthropic/Gemini 是否本期做**：DeepSeek 是主链路（自动+最便宜），
   建议 DeepSeek 先行验证再扩。
