## 一、Kubernetes 原生 / 云原生推理调度框架（最贴近你的"网关+前缀缓存"场景）

### 1. llm-d（IBM / Google / Red Hat 联合开源）
- **GitHub**: https://github.com/llm-d/llm-d
- **核心能力**: 基于 Kubernetes Gateway API Inference Extension (GAIE) 的 **KV Cache Aware Routing**，通过 External Processing Pod (EPP) 与 Envoy 集成，实时追踪 vLLM Pod 的 KV 缓存状态（BlockStored/BlockRemoved 事件），实现**精确前缀缓存路由**。
- **关键组件**:
  - `llm-d-router`: 智能入口，支持 standalone 和 gateway 两种模式
  - `llm-d-kv-cache-manager`: 全局 KV 缓存索引，分片处理
  - `Precise Prefix-Cache Scorer`: 计算每个 Pod 的缓存亲和分数，再结合负载分数做平衡决策
- **生产数据**: Red Hat 博客报道最新达到 **87.4% 缓存命中率** 
- **与你的设计的对应点**: 
  - 它的 `cache-aware-router` 插件配置里的 `session_affinity` 和 `prefix-aware` 算法，跟你的"有界负载一致哈希 + 溢出迁回"思路非常接近
  - 它的"write path"（vLLM Pod 通过 ZMQ 发布缓存事件）对应你的 Profiler 回写机制

### 2. AIBrix（vLLM 生态官方项目）
- **GitHub**: https://github.com/vllm-project/aibrix
- **核心能力**: vLLM 生产栈的网关插件，支持 **Prefix Cache + Load-Aware Routing**。
- **路由算法**:
  - `prefix_cache`: 基于前缀树匹配
  - `prefix_cache_preble`: 基于 Preble 论文的优化前缀调度（但有已知 bug，高并发长文本下会递归栈溢出，v0.5.0 有修复 PR）
- **关键文件**: `pkg/plugins/gateway/algorithms/prefix_cache_preble.go`
- **与你的设计的对应点**:
  - AIBrix 的 `PrefixCache` 路由策略直接实现了"前缀亲和"，但缺少"有界负载"和"预热"机制，你的设计在这些点上更完整
  - 它的 `MetadataStore` 抽象层对应你的 `PrefixStore` 接口（memory / redis 切换）

### 3. vLLM Production Stack
- **文档**: https://docs.vllm.ai/projects/production-stack/
- **核心能力**: 官方生产部署指南，包含 **Prefix-Aware Routing** 和 **KV-Aware Routing** 两种模式。
- **关键教程**:
  - Prefix-aware routing: 基于请求内容前缀选择 replica
  - KV-aware routing: 基于实际 KV 缓存状态选择 replica（需要 replica 上报状态）
- **与你的设计的对应点**: 它的"session affinity + prefix caching"组合，对应你的"亲和层 + 前缀固化"思路

## 二、推理框架自带的路由/负载均衡（本地部署场景）

### 4. SGLang（LMSYS / Berkeley）
- **GitHub**: https://github.com/sgl-project/sglang
- **核心能力**: 从 v0.4 开始内置 **Cache-Aware Load Balancer**。
- **用法**:
  - 单节点多 GPU: `--dp-size 2 --load-balance-method cache_aware`
  - 多节点: 前置 `sgl-router`，配置 `cache_aware` 策略，基于前缀 hash 路由到同一 worker
- **生产数据**: LMSYS 官方 benchmark 显示 **1.9× 吞吐提升，3.8× 缓存命中率提升** 
- **最新进展** (2026-05): 正在推进 DP-attention 场景下的 `prefix_match` 负载均衡，解决单实例内多 DP rank 的前缀缓存打散问题 
- **与你的设计的对应点**: SGLang 的 `cache_aware` 是"纯 hash 路由"，没有负载感知；你的"有界负载一致哈希 + 过载溢出"正好补上了这个缺口

### 5. Ray Serve（Anyscale）
- **文档**: https://docs.ray.io/en/latest/serve/llm/user-guides/prefix-aware-routing.html
- **核心能力**: `PrefixCacheAffinityRouter`，基于字符级前缀树近似追踪各 replica 的缓存状态。
- **生产数据**: 32B 模型上 **TTFT 降低 60%，端到端吞吐提升 40%** 
- **实现细节**: 维护一个 character-level prefix tree，每次路由后插入请求内容并标记 replica；后续请求查询最长公共前缀。负载过高时 fallback 到 Power of Two Choices。
- **与你的设计的对应点**: 它的"前缀树 + 负载 fallback"跟你的"指纹树 + 有界负载溢出"思路一致，但 Ray 的实现是字符级而非 token 级，精度较低

### 6. vLLM（核心引擎）
- **文档**: https://docs.vllm.ai/en/stable/design/prefix_caching/
- **核心能力**: `--enable-prefix-caching` 开启 RadixAttention 前缀缓存，但**本身不做路由决策**，需要上层网关配合。
- **关键配合**: 需要上层网关做 sticky routing / session affinity，否则分布式部署下前缀缓存会失效

## 三、通用 AI Gateway / 代理（多云厂商场景）

### 7. LiteLLM（最活跃的通用 LLM 代理）
- **GitHub**: https://github.com/BerriAI/litellm
- **核心能力**: 支持 100+ 厂商的统一接口，有 **Prompt Caching + Auto-Routing** 组合。
- **关键发现** (2026-07 博客):
  - **Auto-routing 不会破坏 prompt caching**: 99.3% 的模型切回时缓存仍热（1h TTL 场景）
  - **后台预热不值得做**: 只有 4% 的缓存 miss 可通过后台预热避免，且对一般聊天场景反而让总成本增加 0.10% 
  - 但对 agentic 长会话（~190k tokens 前缀），预热可省 0.9% 成本
- **与你的设计的对应点**: LiteLLM 的实测数据直接支撑了你方案中"预热帽按最坏场景测算"和"分阶段目标"的合理性——预热不是银弹，需要严格配额控制

### 8. Portkey（开源网关 + 托管控制平面）
- **GitHub**: https://github.com/Portkey-AI/gateway
- **核心能力**: MIT 协议开源，支持 simple cache 和 semantic cache，以及多模型路由、fallback、成本追踪。
- **状态**: 2026 年被 Palo Alto Networks 收购，继续活跃开发。

### 9. Kong AI Gateway
- **核心能力**: 通过 AI Semantic Cache 插件做向量相似度缓存，支持 Redis 向量存储。
- **限制**: 很多 AI 能力需要企业版许可。

### 10. Apache APISIX + AI 插件
- **博客/教程**: 有完整的"AI Gateway 降低 75% 成本"教程，展示如何用 APISIX 的 `proxy-cache` 和自定义 serverless 插件实现语义缓存。
- **与你的设计的对应点**: 这属于 L0 响应缓存层，跟你的"云侧前缀缓存（L1）+ 响应缓存（L0）"分层架构正交。

## 四、NVIDIA 生态

### 11. NVIDIA Dynamo（原 Triton Dynamo）
- **GitHub**: https://github.com/ai-dynamo/dynamo
- **核心能力**: `dynamo-kv-router`，基于 Rust 实现，支持 **KV-aware routing** 和 **standalone indexer**。
- **关键组件**:
  - `kv-router`: 基于前缀 hash 的路由决策
  - `indexer`: 分片 KV 缓存索引，支持 ZMQ 事件接收
  - `slot-tracker`: 追踪 GPU 显存槽位
- **与你的设计的对应点**: 它的 `standalone-indexer` + `metrics` 模块，对应你的 Profiler + 预热调度器架构。

### 12. Preble: Efficient Distributed Prompt Scheduling for LLM Serving
- **论文**: arXiv:2407.00023
- **核心思想**: 分布式场景下的前缀感知调度，AIBrix 的 `prefix_cache_preble` 算法即来源于此。
- **被引用**: Lodestar 等后续路由论文将其作为基线对比 

### 13. KVCache in the Wild: Characterizing and Optimizing KVCache at a Large Cloud Provider
- **论文**: USENIX ATC 2025
- **核心思想**: 大规模云厂商场景下的 KV 缓存特征分析与优化，对你的"云厂商前缀缓存机制"设计有直接参考价值。

### 14. Lodestar: An Online-Learning LLM Inference Router
- **论文**: arXiv:2606.00946
- **核心思想**: 在线学习的路由器，将缓存命中、延迟、成本作为多目标优化，支持前缀缓存感知。

## 六、社区讨论 / 生产实践

### 15. OpenAI Community: Prompt Cache Routing + `prompt_cache_key`
- **讨论**: OpenAI 社区对 `prompt_cache_key`（替代 `user` 参数）的深度讨论。
- **关键结论**:
  - `prompt_cache_key` 用于缓存路由信号，与前 256 tokens 的 hash 共同决定路由到哪个推理服务器
  - 每前缀建议 ≤15 req/min，高流量时应按 user 维度拆分 `prompt_cache_key` 避免饱和 
- **与你的设计的对应点**: 直接对应你的 `QuotaCoordinator` 中"每前缀 15 rpm 硬约束"和 OpenAI 适配器的 `prompt_cache_options` 注入逻辑。

### 16. nanobot / LocalAI: vLLM Session Affinity
- **Issue**: https://github.com/HKUDS/nanobot/issues/1645
- **核心讨论**: 分布式 vLLM 部署中，同一对话轮次被打到不同 worker 导致前缀缓存失效，需要显式 session-affinity 路由提示。
- **结论**: 只依赖官方文档支持的模式，不引入未文档化的 Azure `x-session-affinity` 语义。

## 三、几个与你设计基线直接相关的关键更新

### 1. OpenAI GPT-5.6 引入了 Cache-Write 收费（重大变化）
以前 OpenAI 是"免费写入"，但 2026-07 发布的 GPT-5.6 家族开始收取 **1.25× base input** 的 cache-write 费用 。这意味着你的 **预热成本模型**需要区分：
- **老模型**（GPT-5.4 及以前）：预热 write 免费，迟到只损失命中率
- **新模型**（GPT-5.6+）：预热 write 本身就有成本，迟到 = 全价 prefill + 额外 write 费

### 2. Anthropic 默认 TTL 在 2026-03 悄悄从 1h 改回 5min
社区有开发者分析了 119,866 次 API 调用，发现 Anthropic 在 2026-03-06 无公告地将默认 TTL 从 1 小时改为 5 分钟，导致部分团队成本浪费 17.1% 。这直接支撑了你设计中 **"TTL×0.45 提前预热"** 和 **"按最坏场景全价测算"** 的保守策略。

### 3. DeepSeek 的 50× 折扣是真实的，但最小前缀未官方公布
DeepSeek v4-flash 的 hit 价格 $0.0028/M 对比 miss $0.14/M 确实是 **50× 差距** ，但官方文档**没有明确写出最小可缓存前缀长度**。你的基线中写的 "~1024 tokens（64-token 单元）" 是社区推断值，建议配置中留注释说明"待官方确认"。

### 4. Gemini 显式缓存的存储费是持续成本
Gemini 3.1 Pro 的 $4.50/MTok/hr 存储费意味着：一个 1M token 的缓存挂 24 小时 = **$108 纯存储成本**，不管读没读 。这解释了为什么你的设计基线里写"长上下文才值得做"——短前缀的存储费会吃掉所有折扣。
